脆弱性を作り込まない実装にする。原因そのものを取り除くので、その脆弱性を狙う攻撃の無効化が期待できる。

🛡 保険的対策

原因そのものは残っていても、攻撃から被害までのどこかで影響を軽減する。根本的解決の代わりではなく、セーフティネットとして考える。

📖 対策文を読むための重要用語集

IPAの対策で出てくる専門語を、支援士で必要な意味に絞って整理。対策名を丸暗記せず『何を分離・照合・制限しているのか』まで理解するための欄です。

プレースホルダ

SQL文で後から値を入れる場所を示す穴。例：WHERE id = ? の「?」。SQL命令と入力値を分離する。

バインド

プレースホルダへ実際の値を割り当てる処理。文字列連結ではなく、入力を「値」としてDBへ渡す。

静的プレースホルダ

DB側でSQLの構造を先に解析し、その後で値を割り当てる方式。構造と値が明確に分離される。

動的プレースホルダ

DB接続ライブラリ側で値をエスケープし、プレースホルダへ組み込む方式。

Prepared Statement

プレースホルダを使う代表的仕組み。SQLの雛形を準備し、後から値を渡す。

Referer

HTTPリクエストが『どのページから来たか』を示すことがあるヘッダ。CSRFでは正規画面からの遷移確認に使えるが、送信されない場合もある。

hiddenパラメータ

フォーム画面には表示されない値。ただしブラウザから送信されるので、hiddenだから秘密という意味ではない。

CSRFトークン／秘密情報

攻撃者が予測困難な値を正規画面へ埋め込み、送信時にサーバ側で一致確認するための値。

POSTメソッド

HTTPで主にリクエスト本文にデータを入れて送る方法。POSTにするだけでCSRFを防げるわけではない。

GETメソッド

主に情報取得に使うHTTPメソッド。パラメータがURLに現れることがあり、秘密情報をURLへ載せないことが重要。

セッションID

サーバが利用者のログイン状態等を識別するID。盗まれるとなりすましにつながるため、一時的な認証情報として扱う。

Session Fixation

攻撃者が知るセッションIDを被害者に使わせ、そのIDがログイン後も有効になることを悪用する攻撃。

Secure属性

CookieをHTTPS通信時だけ送るための属性。HTTPへの誤送信を防ぐ。

HttpOnly属性

JavaScriptからCookieを読み取りにくくする属性。XSS自体を直すのではなくCookie窃取被害を抑える。

エスケープ

HTML等で特別な意味を持つ文字を、その出力文脈で単なるデータとして扱える形にすること。

ホワイトリスト

許可するものを決め、それ以外を拒否する方式。

CR / LF

改行を表す制御文字。HTTPやメールでは行の境界なので、混入すると追加ヘッダ等を作られる原因になる。

Locationヘッダ

HTTPレスポンスでリダイレクト先を示すヘッダ。

X-Frame-Options

ページをframe/iframe内に表示してよいか制御するHTTPレスポンスヘッダ。クリックジャッキング対策で使う。

frame / iframe

Webページ内に別のWebページを表示するHTML機能。クリックジャッキングで重ね合わせに悪用される。

認証

『誰であるか』を確認すること。

認可

認証済み利用者が『そのデータ・機能を操作してよいか』を判定すること。

最小権限

必要最小限の権限だけを与え、侵害時の被害範囲を小さくする考え方。

暗号論的擬似乱数生成器

第三者が現実的に予測できない値を生成する仕組み。セッションIDやCSRF用秘密情報に使う。

1.1

SQLインジェクション

CWE-89

📚 概要

利用者入力を基にSQL文を組み立てる際、入力値が「データ」ではなくSQL構文の一部として解釈され、DBを不正利用される脆弱性。

発生しうる脅威：非公開情報の閲覧、情報の改ざん・消去、認証回避による不正ログイン。

🗺 攻撃の流れ

攻撃者入力値を操作
→
Webアプリ入力をSQL文字列へ連結
→
DB入力をSQL構文として解釈
→
被害閲覧・改ざん・認証回避

❌ 脆弱な実装

検索語・ID・ログイン情報などを文字列連結してSQL文を生成する実装。開発者は『値が入るだけ』と考えていても、DB側には完成したSQL文として渡るため、入力値がSQL構造へ影響できる。

sql = "SELECT * FROM users WHERE id='" + id + "'";
読むポイント：攻撃者が操作できる値と、その値を最終的に解釈する処理の間に、どの境界が欠けているか。

💡 この対策で出る用語

プレースホルダ

SQL文で後から値を入れる場所を示す穴。例：WHERE id = ? の ?。SQL命令と入力値を分離する。

バインド

プレースホルダへ実際の値を割り当てる処理。入力をSQL構文ではなく値としてDBへ渡す。

Prepared Statement

プレースホルダを使う代表的な仕組み。SQLの雛形を準備してから値を渡す。

最小権限

必要最小限の権限だけを与え、侵害時の被害範囲を小さくする考え方。

🏛 IPA公式 第1章｜対策項目フル反映

✅ 根本的解決

1-(i)-a
SQL文の組み立ては全てプレースホルダで実装する。

SQL構造を固定し、外部入力は値としてバインドする。

なぜ効く？

SQLの命令部分と入力値を分離するため、攻撃文字列を入力されても原則としてSQL構文として解釈されない。

脆弱な実装との違い

文字列連結は『入力値がSQL文そのものへ混ざる』。プレースホルダ＋バインドは『SQLの形を固定して、後から値だけ渡す』。

🛡 保険的対策

1-(iii)
エラーメッセージをそのままブラウザに表示しない。

攻撃のヒントを減らす。

1-(iv)
DBアカウントに適切な権限を与える。

突破時の被害範囲を最小化する。

📝 支援士での見抜き方

『SQL文を文字列連結』『入力値をWHERE条件へ直接埋込み』『対策として危険文字だけ削除』を見たら要注意。根本対策はプレースホルダ。

1.2

OSコマンド・インジェクション

CWE-78

📚 概要

外部入力がシェルやOSコマンドの一部として解釈され、Webサーバ上で意図しないコマンドを実行される脆弱性。

発生しうる脅威：サーバ内ファイルの閲覧・改ざん・削除、不正なシステム操作、不正プログラムのダウンロード・実行。

🗺 攻撃の流れ

攻撃者host等の入力を操作
→
Webアプリ入力入りコマンド文字列を生成
→
シェル入力の一部を命令として解釈
→
被害任意コマンド実行

❌ 脆弱な実装

外部入力を含む文字列を、シェルを起動できる言語機能へ渡す実装。『引数として使うつもり』でも、シェルがメタ文字等を命令として解釈できると境界が崩れる。

system("ping " + host);
読むポイント：攻撃者が操作できる値と、その値を最終的に解釈する処理の間に、どの境界が欠けているか。
🏛 IPA公式 第1章｜対策項目フル反映

✅ 根本的解決

2-(i)
シェルを起動できる言語機能の利用を避ける。

入力がシェル文法として解釈される経路そのものをなくす。

なぜ効く？

シェルを呼ばなければ、外部入力にシェルのメタ文字が含まれてもOSコマンドの構文として解釈される入口をなくせる。

答案での言い方

『入力値を無害化する』より、『シェルを起動する機能を使用せず専用APIを使用する』と原因を断つ形で書く。

🛡 保険的対策

2-(ii)
シェル利用時は引数を構成する全変数をチェックし、許可した処理だけを実行する。

攻撃入力と実行可能処理を限定する。

📝 支援士での見抜き方

『system/open等』『入力値をコマンド引数へ連結』がシグナル。SQLiとの違いは最終的な解釈主体がDBではなくシェル/OSであること。

1.3

パス名パラメータの未チェック／ディレクトリ・トラバーサル

CWE-22

📚 概要

外部入力でサーバ内のファイル名やパスを直接指定できるため、想定外ディレクトリのファイルへアクセスされる脆弱性。

発生しうる脅威：公開を想定しないファイルの閲覧、設定・機密情報の漏えい、場合によってはファイル変更。

🗺 攻撃の流れ

攻撃者ファイル名/パスを操作
→
Webアプリ基準パスと単純連結
→
OS相対パスを正規化
→
被害許可領域外のファイルへ到達

❌ 脆弱な実装

`/data/` の後ろへ利用者指定ファイル名を単純連結するなど、入力値がそのまま物理パスになる実装。文字列上では安全に見えてもOSのパス正規化後に境界外へ出ることがある。

open("/data/" + filename);
読むポイント：攻撃者が操作できる値と、その値を最終的に解釈する処理の間に、どの境界が欠けているか。
🏛 IPA公式 第1章｜対策項目フル反映

✅ 根本的解決

3-(i)-a
外部パラメータでサーバ内ファイル名を直接指定する実装を避ける。

外部入力を物理パスそのものにしない。

なぜ効く？

利用者入力を物理ファイルパスとして扱わなければ、../ 等で想定ディレクトリ外へ移動する余地そのものをなくせる。

実装イメージ

利用者には論理IDを渡し、サーバ側でIDと固定ファイル名を対応付ける。外部入力から直接パスを組み立てない。

🛡 保険的対策

3-(ii)
ファイルへのアクセス権限を正しく管理する。

OS/サーバ権限で被害範囲を抑える。

3-(iii)
ファイル名をチェックする。

パス指定文字列やエンコード後の表現に注意する。

📝 支援士での見抜き方

`../`削除だけを根本対策として選ばせる問題に注意。最終的には『外部入力で物理パスを直接指定させない』設計が強い。

1.4

セッション管理の不備

Session Management

📚 概要

セッションIDの生成・受渡し・更新・有効期限管理に不備があり、第三者が利用者のセッションを奪う脆弱性。

発生しうる脅威：セッションIDの推測・盗用・固定化により、ログイン中利用者へのなりすまし。

🗺 攻撃の流れ

攻撃者IDを推測/盗用/固定
→
利用者そのIDでログイン
→
Webアプリ同じIDを認証済みとして継続
→
被害セッション・ハイジャック

❌ 脆弱な実装

予測可能なID、URLへのID露出、ログイン前後で同じIDを使い続ける、固定値・長すぎる有効期限など。セッションIDは単なる識別子ではなく一時的な認証情報。

// login成功後も session_id を変更しない
読むポイント：攻撃者が操作できる値と、その値を最終的に解釈する処理の間に、どの境界が欠けているか。

💡 この対策で出る用語

セッションID

ログイン状態を識別するID。盗まれるとなりすましにつながるため、一時的な認証情報として扱う。

Session Fixation

攻撃者が知るセッションIDを被害者に使わせ、そのIDがログイン後も有効になることを悪用する攻撃。

Secure属性

CookieをHTTPS通信時だけ送る属性。HTTPへの誤送信を防ぐ。

暗号論的擬似乱数

第三者が現実的に予測できない値を生成する仕組み。セッションIDやCSRFトークンに使う。

🏛 IPA公式 第1章｜対策項目フル反映

✅ 根本的解決

4-(i)
セッションIDを推測困難にする。

暗号論的擬似乱数等で予測を困難にする。

なぜ効く？

第三者が有効なセッションIDを推測して本人になりすます攻撃を困難にする。

注意

連番・時刻・ユーザIDなど推測材料になる値からIDを生成しない。

4-(ii)
セッションIDをURLパラメータに格納しない。

Referer等からの漏えい経路を避ける。

なぜ効く？

URLは履歴・ログ・Refererなど複数箇所へ残り得る。セッションIDをURLから外すことで漏えい経路を減らす。

試験ポイント

『URLにセッションID』を見たら、Referer等を介した漏えいを疑う。

4-(iii)
HTTPS用Cookieにsecure属性を加える。

平文HTTPへのCookie送信を防ぐ。

なぜ効く？

Secure属性付きCookieはHTTPS通信でのみ送られるため、HTTP通信へセッションCookieが流れるのを防ぐ。

注意

Secure属性だけでCookie盗用全般を防げるわけではない。

4-(iv)-a
ログイン成功後に新しいセッションを開始する。

既存IDを無効化しSession Fixationを断つ。

なぜ効く？

ログイン前に攻撃者が知っていたセッションIDをログイン成功後に無効化するため、Session Fixationが成立しにくくなる。

実装イメージ

認証成功 → 新しいセッションID発行 → 古いIDを無効化 → 認証済み状態を新IDへ引き継ぐ。

4-(iv)-b
ログイン後に別の秘密情報を発行し、ページ遷移ごとに確認する。

4-(iv)-aを採れない場合の別方式。

🛡 保険的対策

4-(v)
セッションIDを固定値にしない。

漏えいIDの長期悪用を抑える。

4-(vi)
Cookieの有効期限設定に注意する。

盗まれたCookieが使える期間を短くする。

📝 支援士での見抜き方

Secure/HttpOnly/SameSiteの役割、Session Fixation、ログイン時ID再生成を切り分ける。

1.5

クロスサイト・スクリプティング（XSS）

CWE-79

📚 概要

外部入力やDB等から得た文字列をWebページへ出力するときの処理が不適切で、ブラウザにスクリプト等として解釈される脆弱性。

発生しうる脅威：偽画面表示、利用者権限での不正操作、Cookie等の情報漏えい。

🗺 攻撃の流れ

攻撃者細工した入力を保存/送信
→
Webアプリ安全化せず出力
→
ブラウザHTML/Scriptとして解釈
→
被害偽画面・不正操作等

❌ 脆弱な実装

入力値をinnerHTMLやHTML本文・属性へそのまま埋め込む実装。XSSは入力時点ではなく『どの文脈へ出力され、ブラウザが何として解釈するか』が核心。

element.innerHTML = userInput;
読むポイント：攻撃者が操作できる値と、その値を最終的に解釈する処理の間に、どの境界が欠けているか。

💡 この対策で出る用語

エスケープ

HTML等で特別な意味を持つ文字を、その文脈で単なるデータとして扱える形にする処理。

HttpOnly属性

JavaScriptからCookieを読み取りにくくする属性。XSS自体を直すのではなくCookie窃取被害を抑える。

🏛 IPA公式 第1章｜対策項目フル反映

✅ 根本的解決

5-(i)
出力する全要素にエスケープ処理を施す。

HTML本文・属性等の出力文脈で安全化する。

なぜ効く？

ブラウザが外部入力をHTMLタグやスクリプトとしてではなく、画面に表示する文字データとして解釈するようにする。

重要

『入力時に危険文字を消す』ではなく、HTML本文・属性など出力先の文脈に応じて出力時に処理する。

5-(ii)
URL出力はhttp://、https://で始まるものだけを許可する。

危険なスキームを許可しない。

なぜ効く？

javascript: など、クリック時にスクリプトを実行できるURLスキームを排除できる。

試験ポイント

URLだからHTMLエスケープだけで十分、とは限らない。URLの方式自体を制限する。

5-(iii)
script要素の内容を動的に生成しない。

外部入力をJavaScriptコードへ混ぜない。

なぜ効く？

JavaScriptコードの中へ外部入力を混ぜる設計自体を避けることで、入力がコードへ変化する境界をなくす。

注意

HTML用エスケープをJavaScript文脈へそのまま流用しない。

5-(iv)
任意サイトのスタイルシートを取り込めるようにしない。

外部CSS経由の危険な解釈経路を作らない。

5-(vi)
HTML入力を許可する場合、構文解析し許可要素だけを抽出する。

ホワイトリスト方式で構造として安全化する。

なぜ効く？

HTMLを単なる文字列として置換するのではなく構造として解析し、許可したタグ・属性だけを残せる。

違い

ブラックリストは未知の表現を漏らしやすい。許可リスト方式は受け入れる範囲を先に限定する。

5-(viii)
Content-Typeにcharsetを指定する。

想定外文字コード解釈を防ぐ。

🛡 保険的対策

5-(v)
入力値の内容チェックを行う。

攻撃入力を減らすが出力時対策の代替ではない。

5-(vii)
HTML入力からスクリプト該当文字列を排除する。

ブラックリスト方式なので補助策として扱う。

5-(ix)
CookieにHttpOnlyを加えTRACEを無効化する。

XSS時のCookie漏えいを低減する。

📝 支援士での見抜き方

『入力値をチェックしたからXSS対策完了』は危険。支援士では出力時エスケープとHttpOnly/CSP等の補助策を分けて考える。

1.6

CSRF

CWE-352

📚 概要

ログイン済み利用者からの要求が、本当に本人の意図した要求か識別できず、外部サイトから意図しない処理を実行させられる脆弱性。

発生しうる脅威：意図しない情報発信、設定変更、パスワード変更、退会など。

🗺 攻撃の流れ

攻撃者罠ページを用意
→
利用者ログイン済みで罠を閲覧
→
ブラウザCookie付き要求を送信
→
正規サイト本人の意図確認なしで処理

❌ 脆弱な実装

セッションCookieが付いていれば正当な要求として状態変更を行う実装。Cookieはブラウザが自動送信するため『本人が意図した』証明にはならない。

POST /change-email  // Cookieのみで処理
読むポイント：攻撃者が操作できる値と、その値を最終的に解釈する処理の間に、どの境界が欠けているか。

💡 この対策で出る用語

hiddenパラメータ

フォーム画面には表示されない値。見えないだけで改変可能なので、hiddenだから秘密という意味ではない。

CSRFトークン

攻撃者が予測困難な値を正規画面へ埋め込み、送信時にサーバ側で照合するための値。

POST

HTTPリクエスト本文へデータを入れて送る代表的メソッド。POSTにするだけではCSRF対策にならない。

Referer

HTTPリクエストがどのページから来たかを示すことがあるヘッダ。CSRFで正規画面遷移の確認材料になる。

暗号論的擬似乱数

第三者が現実的に予測できない値を生成する仕組み。セッションIDやCSRFトークンに使う。

🏛 IPA公式 第1章｜対策項目フル反映

✅ 根本的解決

6-(i)-a
POST＋hidden秘密情報を使い、正しい場合だけ処理する。

攻撃者が知り得ない値を正規画面遷移で埋め込み照合する。

なぜ効く？

攻撃者サイトは被害者のCookieを使わせることはできても、正規画面に埋め込まれた予測困難な秘密情報までは通常知ることができない。

流れ

正規画面表示 → CSRFトークンをhiddenへ埋込み → POST送信 → サーバ側で保存値と照合 → 一致時だけ処理。

6-(i)-b
処理直前に再度パスワード入力を求める。

Cookie自動送信だけでは重要処理を完了できなくする。

なぜ効く？

Cookieはブラウザが自動送信するが、本人のパスワードを攻撃者サイトが自動で入力することはできない。

向いている場面

パスワード変更・退会など特に重要な操作の直前確認。

6-(i)-c
Refererが正しいリンク元か確認する。

正規画面遷移を確認する。副作用も理解する。

なぜ効く？

正規サイト内の画面から遷移した要求かをRefererで確認し、外部の罠ページから来た要求を拒否する。

注意

Refererが送信されない環境もあるため、利用条件・副作用を理解する。

🛡 保険的対策

6-(ii)
重要操作後、登録済みメールへ自動通知する。

攻撃自体は防げないが被害を早期発見する。

📝 支援士での見抜き方

XSSとの違いは『正規サイト上で攻撃コードを実行する必要はない』こと。秘密情報/CSRFトークンの照合が根本。

1.7

HTTPヘッダ・インジェクション

CWE-113

📚 概要

外部入力をHTTPレスポンスヘッダへ出力する際、改行コード等を悪用され、任意ヘッダやレスポンス内容を挿入される脆弱性。

発生しうる脅威：任意Cookieの設定、キャッシュ汚染、偽コンテンツ挿入など。

🗺 攻撃の流れ

攻撃者改行を含む入力
→
Webアプリ入力をヘッダへ直接出力
→
HTTP応答追加ヘッダ/本文として解釈
→
被害Cookie設定・偽応答等

❌ 脆弱な実装

LocationやSet-Cookie等のHTTPヘッダ値へ外部入力を文字列として直接出力し、改行を許してしまう実装。

responseHeader("Location: " + nextUrl);
読むポイント：攻撃者が操作できる値と、その値を最終的に解釈する処理の間に、どの境界が欠けているか。

💡 この対策で出る用語

CR/LF

HTTPやメールで行の境界を表す改行文字。混入すると新しいヘッダを挿入される原因になる。

🏛 IPA公式 第1章｜対策項目フル反映

✅ 根本的解決

7-(i)-a
ヘッダを直接出力せずヘッダ出力APIを使う。

CR/LFをHTTP構造へ直接混ぜる設計を避ける。

なぜ効く？

生の文字列としてHTTPヘッダを組み立てずAPIに任せることで、外部入力のCR/LFがヘッダ境界として扱われる危険を避ける。

試験ポイント

『Location: + 入力値』のような直接連結を見たら要注意。

7-(i)-b
安全なAPIが使えない場合、改行を許可しない処理を実装する。

新しいヘッダ/本文境界を作れなくする。

🛡 保険的対策

7-(ii)
外部入力の改行コードを削除する。

CR/LF攻撃を減らす。正当な改行への副作用に注意。

📝 支援士での見抜き方

HTTPレスポンスヘッダでCRLFが境界になる。メールヘッダ・インジェクションとの違いは出力先。

1.8

メールヘッダ・インジェクション

CWE-93

📚 概要

外部入力をTo/Cc/Bcc/Subject等のメールヘッダへ不適切に出力し、改行コードで任意ヘッダや本文を挿入される脆弱性。

発生しうる脅威：任意宛先へのメール送信、ヘッダ挿入、本文改変、第三者中継的な悪用。

🗺 攻撃の流れ

攻撃者宛先/件名入力を改変
→
Webアプリメールヘッダへ直接反映
→
メール処理改行後を新ヘッダとして解釈
→
被害任意宛先・本文改変

❌ 脆弱な実装

hiddenパラメータやフォーム入力をそのまま宛先・件名等へ設定する実装。外部入力が『メールの制御情報』へ直接入ることが問題。

mail(to=userInput, subject=subjectInput, ...);
読むポイント：攻撃者が操作できる値と、その値を最終的に解釈する処理の間に、どの境界が欠けているか。

💡 この対策で出る用語

CR/LF

HTTPやメールで行の境界を表す改行文字。混入すると新しいヘッダを挿入される原因になる。

hiddenパラメータ

フォーム画面には表示されない値。見えないだけで改変可能なので、hiddenだから秘密という意味ではない。

🏛 IPA公式 第1章｜対策項目フル反映

✅ 根本的解決

8-(i)-a
メールヘッダを固定値にし、外部入力は本文へ出力する。

制御領域へ攻撃者入力を入れない。

なぜ効く？

To/Cc/Bcc/Subjectなどメールの制御情報へ外部入力を入れなければ、改行で追加ヘッダを作る入口がなくなる。

注意

hiddenで宛先を持たせても安全にはならない。クライアント値は改変可能。

8-(i)-b
固定できない場合はメール送信用APIを使う。

安全なメール構造生成に任せる。

8-(ii)
HTMLで宛先を指定しない。

hidden等の改変可能値を宛先にしない。

🛡 保険的対策

8-(iii)
外部入力の改行コードを削除する。

追加ヘッダ挿入を難しくする。

📝 支援士での見抜き方

『hiddenだから安全』は誤り。クライアントから送られる値は攻撃者が変更できる。

1.9

クリックジャッキング

Direct CWEなし

📚 概要

正規サイトをframe/iframe等で重ね、利用者を視覚的に騙して意図しないクリック操作を実行させる脆弱性。

発生しうる脅威：意図しない情報発信、退会、設定変更など。マウス操作だけで実行可能な重要処理は特に注意。

🗺 攻撃の流れ

攻撃者罠ページへ透明/重ね合わせ表示
→
利用者見えているUIをクリック
→
実際の正規ページ背後の重要ボタンが押される
→
被害意図しない処理

❌ 脆弱な実装

ログイン後の重要操作ページを他サイトのframe内に表示でき、クリックだけで処理完了する設計。

// 重要ページが外部iframe内で表示可能
読むポイント：攻撃者が操作できる値と、その値を最終的に解釈する処理の間に、どの境界が欠けているか。

💡 この対策で出る用語

X-Frame-Options

ページをframe/iframe内に表示してよいかを制御するHTTPレスポンスヘッダ。

frame/iframe

Webページ内に別ページを表示するHTML機能。クリックジャッキングで重ね合わせに悪用される。

🏛 IPA公式 第1章｜対策項目フル反映

✅ 根本的解決

9-(i)-a
X-Frame-Optionsで他ドメインからのframe/iframe読み込みを制限する。

攻撃者サイト上へ正規ページを重ねる土台をなくす。

なぜ効く？

正規ページを攻撃者サイトのframe/iframe内へ表示できなくすることで、透明化・重ね合わせによるクリック誘導の土台をなくす。

覚え方

クリックジャッキング → frame制御 → X-Frame-Options。

9-(i)-b
処理直前に再度パスワード入力を求める。

誘導クリックだけでは処理完了できなくする。

🛡 保険的対策

9-(ii)
重要処理をマウス操作だけで完了できないようにする。

視覚誘導だけでの攻撃成功率を下げる。

📝 支援士での見抜き方

CSRFと似るが、クリックジャッキングは『見た目を騙して実際に利用者へクリックさせる』。frame制御が重要。

1.10

バッファオーバーフロー

CWE-119

📚 概要

確保したメモリ領域の境界を超えてデータを書き込み、異常終了や任意コード実行等につながる脆弱性。

発生しうる脅威：プログラム異常終了、メモリ破壊、不正コード実行など。

🗺 攻撃の流れ

攻撃者想定以上の入力
→
プログラム固定長領域へ無制限コピー
→
メモリ隣接領域まで破壊
→
被害異常終了/コード実行

❌ 脆弱な実装

C/C++等で固定長バッファへ長さ確認なしにデータをコピーするなど、直接メモリ操作可能な部分で境界チェックが不足する実装。

char buf[16]; strcpy(buf, input);
読むポイント：攻撃者が操作できる値と、その値を最終的に解釈する処理の間に、どの境界が欠けているか。
🏛 IPA公式 第1章｜対策項目フル反映

✅ 根本的解決

10-(i)-a
直接メモリにアクセスできない言語で記述する。

境界外メモリ書換えの実装クラスを避ける。

なぜ効く？

言語処理系がメモリ境界を管理するため、典型的な境界外書込みを実装として作り込みにくくなる。

試験ポイント

C/C++等のメモリ安全性と、Java等のメモリ管理言語を切り分ける。

10-(i)-b
直接メモリへアクセスできる言語で記述する部分を最小限にする。

危険領域を限定して集中確認する。

10-(ii)
脆弱性が修正されたライブラリを使用する。

既知脆弱性のある依存部品を残さない。

🛡 保険的対策

IPA第1章では、この節に独立した保険的対策の項目はありません。

📝 支援士での見抜き方

Webアプリでもネイティブライブラリを呼ぶ場合に注意。『直接メモリを扱える言語か』が切り分けポイント。

1.11

アクセス制御や認可制御の欠落

Access Control

📚 概要

非公開情報を守る認証機能や、ログイン利用者ごとに許可操作を分ける認可機能が不足している脆弱性。

発生しうる脅威：非公開情報の閲覧、他人データの変更、他利用者へのなりすまし操作。

🗺 攻撃の流れ

攻撃者URL/ID/機能を直接指定
→
Webアプリ認証/認可確認が不足
→
内部処理対象データ・機能へ到達
→
被害他人データ閲覧・変更

❌ 脆弱な実装

メールアドレス等の公開され得る情報だけで非公開情報を閲覧できる、またはログイン後にIDを書き換えるだけで他人のデータへアクセスできる実装。

record = db.find(request.id); return record; // 所有者確認なし
読むポイント：攻撃者が操作できる値と、その値を最終的に解釈する処理の間に、どの境界が欠けているか。

💡 この対策で出る用語

認証

利用者が誰であるかを確認すること。

認可

認証済み利用者がそのデータ・機能を操作してよいか判定すること。

最小権限

必要最小限の権限だけを与え、侵害時の被害範囲を小さくする考え方。

🏛 IPA公式 第1章｜対策項目フル反映

✅ 根本的解決

11-(i)
必要なサイトには秘密情報入力を必要とする認証機能を設ける。

非公開情報への入口を本人確認で守る。

なぜ効く？

非公開情報へ到達する前に本人確認を要求し、誰でもURLを知れば閲覧できる状態をなくす。

注意

認証だけでは他人のデータへのアクセスは防げない。次の認可が必要。

11-(ii)
認証に加えて認可制御を実装する。

セッション上の本人と対象・操作権限をサーバ側で照合する。

なぜ効く？

サーバ側で『ログイン中の本人』と『操作対象の所有者・必要権限』を照合するため、IDを書き換えるだけの他人データアクセスを防げる。

最重要

認証＝誰か、認可＝何をしてよいか。BOLA/IDORでは認可不足を疑う。

🛡 保険的対策

IPA第1章では、この節に独立した保険的対策の項目はありません。

📝 支援士での見抜き方

BOLA/IDORへ直結。『ログインできている』ことと『その対象を操作してよい』ことは別。
